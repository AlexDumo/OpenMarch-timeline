route A (first follow-the-leader) route B (the next one) entry: getting from A onto B problem

1A ripple from one route into the next

Six marchers follow route A, two counts apart. Each one reaches A's end on a different count (the ripple). Each takes a 5-count straight entry onto B, then follows B. Play it, then press Move route B to see what an edit does to each way of storing the entry.

count 0
Entry stored on route B (proposed)
B holds one setting: "straight, 5 counts". Each marcher's entry is worked out from when it leaves A. When B moves, every entry re-aims at B's new start.
Entry stored as its own moves
Six small straight moves, one per marcher, at fixed counts and fixed end points. They look the same until B moves. Then they still end where B used to start, and marchers jump.
Why entry-on-route: both play back the same until something changes. The ripple's timing and B's position belong to the routes, so the entry should be worked out from them, not stored as copies that can go out of date. Six separate moves would also each need to be kept in step with A's ripple when A is edited.

2How long is an entry?

The marcher leaves A's end and has to cover the gap to B's start. How many counts does that take? Each dot is one count.

My lean: B by default, with A as an override. Counts worked out from distance keep steps marchable without any typing. Typing a count is still allowed when the music calls for it, and a big step gets flagged (your Q5: warn only).

3One rule, two uses

The entry that takes a marcher from A onto B is the same rule as option A in Q4 (rejoin after a higher layer lets go). Both answer one question: how does a marcher get onto a route it isn't on? Building it once means one setting, one piece of resolver logic, one bound to prove.
